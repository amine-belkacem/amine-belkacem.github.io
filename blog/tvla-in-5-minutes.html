TVLA in 5 minutes: does the power consumption depend on the data?

20 November 20265 min readProject: aes128-sidechannel-lab

A side-channel attack answers a narrow question: "can this attack recover the key?". Test Vector Leakage Assessment (TVLA) asks a broader one: "does the power consumption depend on the data at all?". Here is how it works, measured on my own AES-128 core.

The recipe

  1. Run many encryptions. For each one, flip a coin: encrypt either a fixed plaintext, or a random one.
  2. Record the power trace of each encryption (here: simulated from the VHDL core, with Gaussian noise σ = 8 added).
  3. At every point in time (here: every clock edge), compare the two groups with Welch's t-test.
  4. If |t| > 4.5 anywhere, the device leaks.

The logic: if the consumption did not depend on the data, the fixed group and the random group would have the same mean, and t would stay small. The threshold 4.5 keeps the false-alarm rate very low even when you test thousands of points.

A control is essential: split the random group in two at random and run the same test. Those two halves really are identical in distribution, so that test must stay below 4.5. If it does not, the setup is broken, not the device.

On my unprotected core (40,000 encryptions)

  • The core leaks on 10 of the 11 clock edges, up to |t| = 133 on the last round.
  • The test crosses 4.5 after only 43 traces.
  • The control never exceeds 1.92. The setup is sound.

The edge that fooled the test

One edge passes: round 4, t = −0.8. That is not protection. For the fixed plaintext, the state register happens to flip exactly 64 bits on that edge, which is precisely the average for random plaintexts (64.06). The two groups have the same mean, so a test on means cannot separate them, even though the leakage is there.

TVLA can miss a leak. It cannot invent one. A pass on one point means "no difference of means here", never "secure". I checked this one from the register values before writing it down.

On a countermeasure

The first countermeasure I built inserts a random number of dummy rounds (up to D = 15) before the real ones. With 40,000 traces and no added noise:

D = 0D = 15
max |t| (outside the plaintext-load edge)29021.8
traces until |t| > 4.5202,238

Hiding lowers the statistic a lot, but the protected core still fails TVLA, as it should: the leakage is still there, only spread over time. Against a real key-recovery attack, it costs an unprofiled attacker 28 times more traces, but a profiled attacker only 3.7 times more.

That is the value of TVLA: it does not tell you how hard an attack is, but it tells you quickly and honestly whether there is anything to attack.

La TVLA en 5 minutes : la consommation dépend-elle des données ?

20 novembre 20265 min de lectureProjet : aes128-sidechannel-lab

Une attaque par canal auxiliaire répond à une question étroite : « cette attaque retrouve-t-elle la clé ? ». La TVLA (Test Vector Leakage Assessment) pose une question plus large : « la consommation dépend-elle des données, tout simplement ? ». Voici comment elle fonctionne, mesurée sur mon propre cœur AES-128.

La recette

  1. Lancer beaucoup de chiffrements. Pour chacun, tirer à pile ou face : chiffrer un texte clair fixe, ou un texte aléatoire.
  2. Enregistrer la trace de consommation de chaque chiffrement (ici simulée depuis le cœur VHDL, avec un bruit gaussien σ = 8).
  3. À chaque instant (ici, chaque front d'horloge), comparer les deux groupes avec un test t de Welch.
  4. Si |t| > 4,5 quelque part, le circuit fuit.

L'idée : si la consommation ne dépendait pas des données, les deux groupes auraient la même moyenne et t resterait petit. Le seuil de 4,5 garde un taux de fausse alarme très bas même en testant des milliers de points.

Un témoin est indispensable : couper le groupe aléatoire en deux au hasard et refaire le même test. Ces deux moitiés ont vraiment la même distribution, donc ce test doit rester sous 4,5. Sinon, c'est le montage qui est faux, pas le circuit.

Sur mon cœur non protégé (40 000 chiffrements)

  • Le cœur fuit sur 10 des 11 fronts d'horloge, jusqu'à |t| = 133 au dernier tour.
  • Le test dépasse 4,5 après seulement 43 traces.
  • Le témoin ne dépasse jamais 1,92. Le montage est sain.

Le front qui a trompé le test

Un front passe : le tour 4, t = −0,8. Ce n'est pas une protection. Pour le texte clair fixe, le registre d'état bascule exactement 64 bits sur ce front, soit pile la moyenne pour des textes aléatoires (64,06). Les deux groupes ont la même moyenne, donc un test sur les moyennes ne peut pas les séparer, alors que la fuite est bien là.

La TVLA peut rater une fuite. Elle ne peut pas en inventer une. Un point qui passe veut dire « pas de différence de moyenne ici », jamais « sûr ». J'ai vérifié celui-ci à partir des valeurs du registre avant de l'écrire.

Sur une contre-mesure

La première contre-mesure que j'ai construite insère un nombre aléatoire de tours factices (jusqu'à D = 15) avant les vrais. Avec 40 000 traces, sans bruit ajouté :

D = 0D = 15
|t| max (hors front de chargement du texte clair)29021,8
traces avant |t| > 4,5202 238

Le masquage temporel fait beaucoup baisser la statistique, mais le cœur protégé échoue toujours à la TVLA, et c'est normal : la fuite est toujours là, seulement étalée dans le temps. Face à une vraie attaque, il coûte 28 fois plus de traces à un attaquant non profilé, mais seulement 3,7 fois plus à un attaquant profilé.

C'est tout l'intérêt de la TVLA : elle ne dit pas à quel point une attaque est difficile, mais elle dit vite et honnêtement s'il y a quelque chose à attaquer.

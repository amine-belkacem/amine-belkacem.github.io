Why ONNX Runtime drifts by up to 50 LSB on my laptop

20 November 20264 min readProject: int8-neon-inference-pi5

I am writing my own int8 inference engine in C for a small EuroSAT land-use CNN. Before writing any C, I needed a reference I could trust. ONNX Runtime was supposed to be that reference. On my laptop, it gave a different answer depending on one setting.

The setup

The model is an int8 ONNX graph in QDQ format. I turned it into 22 integer operations and ran them in NumPy with nothing but integer arithmetic: int8 activations, int32 accumulators, and a fixed-point requantization (x * m0 + 2^(s-1)) >> s. That is the definition my C engine has to match bit for bit.

Then I compared it with ONNX Runtime on the 4,050 test tiles.

With graph optimisations off: almost perfect

ONNX Runtime evaluates the QDQ graph op by op in float32. My reference predicts the same class on all 4,050 tiles, and 99.90 % of the 40,500 int8 logits are identical. The other 40 are off by exactly 1 LSB: rounding ties (ONNX Runtime rounds half to even, I round half up) and float32 error close to a tie. Fine.

With the default optimisations: a different model

Same model, same inputs, default settings. Only 73 % of the logits were identical, some were off by 50 LSB, and the top-1 class changed on 10 tiles.

Dumping the optimised graph showed that ONNX Runtime had fused each DQ → Conv → Q into a QLinearConv. That is expected. The size of the gap was not.

The cause is the CPU

My laptop has an AMD Ryzen 3 7320U: AVX2, but no AVX-VNNI. On that instruction set, the int8 kernel multiplies uint8 activations by int8 weights with VPMADDUBSW. That instruction adds two neighbouring products and saturates the sum to int16.

255 × 127 × 2 = 64,770   >   32,767  (int16 max)

So whenever two large activations meet two large weights, the partial sum is clipped before it ever reaches the int32 accumulator.

To check the explanation, I added that saturation to my reference (a diagnostic-only version of the convolution). It then matches ONNX Runtime's optimised output on 99.94 % of the logits, with the rest within 3 LSB. On GitHub's CI runner, whose CPU has VNNI, the optimised path stays within 1 LSB of my reference. The hypothesis holds on both machines.

Why nobody notices

Accuracy barely moves: 98.40 % vs 98.42 %. If you only look at the accuracy, the two runs look identical. If you compare outputs byte for byte, they are not the same model.

Takeaway. "ONNX Runtime int8" is not one well-defined result. It depends on the instruction set underneath. If you validate a quantized model, validate it on the CPU it will run on, and compare outputs, not only accuracy.

That is why the comparison that counts for my engine will be made on the Raspberry Pi 5: ARM builds use different kernels, and that is the target.

Pourquoi ONNX Runtime s'écarte jusqu'à 50 LSB sur mon portable

20 novembre 20264 min de lectureProjet : int8-neon-inference-pi5

J'écris mon propre moteur d'inférence int8 en C pour un petit CNN de classification d'images satellite (EuroSAT). Avant d'écrire la moindre ligne de C, il me fallait une référence fiable. ONNX Runtime devait être cette référence. Sur mon portable, sa réponse changeait selon un seul réglage.

Le montage

Le modèle est un graphe ONNX int8 au format QDQ. Je l'ai transformé en 22 opérations entières, exécutées en NumPy uniquement en arithmétique entière : activations int8, accumulateurs int32 et une requantification en virgule fixe (x * m0 + 2^(s-1)) >> s. C'est la définition que mon moteur C devra reproduire au bit près.

Puis je l'ai comparée à ONNX Runtime sur les 4 050 tuiles de test.

Optimisations du graphe désactivées : presque parfait

ONNX Runtime évalue alors le graphe QDQ opération par opération en float32. Ma référence prédit la même classe sur les 4 050 tuiles, et 99,90 % des 40 500 logits int8 sont identiques. Les 40 autres diffèrent d'exactement 1 LSB : égalités d'arrondi (ONNX Runtime arrondit au pair, moi vers le haut) et erreur float32 près d'une égalité. Rien d'anormal.

Optimisations par défaut : un autre modèle

Même modèle, mêmes entrées, réglages par défaut. Seulement 73 % des logits étaient identiques, certains s'écartaient de 50 LSB, et la classe prédite changeait sur 10 tuiles.

En inspectant le graphe optimisé, on voit qu'ONNX Runtime a fusionné chaque DQ → Conv → Q en QLinearConv. C'est attendu. L'ampleur de l'écart, non.

La cause : le processeur

Mon portable a un AMD Ryzen 3 7320U : AVX2, mais pas AVX-VNNI. Sur ce jeu d'instructions, le noyau int8 multiplie les activations uint8 par les poids int8 avec VPMADDUBSW. Cette instruction additionne deux produits voisins et sature la somme sur 16 bits.

255 × 127 × 2 = 64 770   >   32 767  (maximum int16)

Dès que deux grandes activations rencontrent deux grands poids, la somme partielle est écrêtée avant même d'atteindre l'accumulateur int32.

Pour vérifier, j'ai ajouté cette saturation à ma référence (une version de diagnostic de la convolution). Elle colle alors à la sortie optimisée d'ONNX Runtime sur 99,94 % des logits, le reste à moins de 3 LSB. Sur la machine de CI de GitHub, dont le processeur a VNNI, le chemin optimisé reste à 1 LSB de ma référence. L'hypothèse tient sur les deux machines.

Pourquoi personne ne le remarque

La précision bouge à peine : 98,40 % contre 98,42 %. À ne regarder que la précision, les deux exécutions semblent identiques. En comparant les sorties octet par octet, ce n'est pas le même modèle.

À retenir. « ONNX Runtime int8 » n'est pas un résultat unique : il dépend du jeu d'instructions. Pour valider un modèle quantifié, validez-le sur le processeur cible, et comparez les sorties, pas seulement la précision.

C'est pour ça que la comparaison qui compte pour mon moteur se fera sur le Raspberry Pi 5 : les versions ARM utilisent d'autres noyaux, et c'est la cible.
